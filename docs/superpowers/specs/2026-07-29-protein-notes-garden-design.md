## 1. 背景与目标

作者是蛋白质／酶方向的博士生，已有一个 Astro 学术主页（`passion4ever.org`）。这个站用来记录：

- 蛋白质基础知识（氨基酸的一/三字母代号、中文名、化学结构、理化性质等）
- 算法与方法的个人理解（flow matching、AlphaFold 等）

明确排除的形态：**不是 blog** —— 不要时间线、不要「第 N 篇文章」、不要发布仪式感。

核心使用场景是**回看**：几个月后想起「二硫键那事儿」，能快速找到，并顺着链接跳到相关概念。

### 成功标准

1. 想到什么就能写一篇，不需要先决定它「属于哪一章」
2. 回看时既能搜到，也能靠概念之间的链接跳转
3. 化学结构图不需要手工找图、存图
4. 写完 `git push` 就上线，没有别的步骤

## 2. 内容模型与呈现形式

这两件事是分开的，容易混淆，所以分开说：

**内容模型是数字花园。** 每篇是一个**原子概念**（「二硫键」「米氏方程」「flow matching」），没有时间顺序，没有章节编号，靠 `[[双向链接]]` 和标签互联。文件名是英文 slug，标题是中文。

- 为什么不用分层手册：`flow matching` 同时属于「生成模型」「与 diffusion 的对比」「蛋白质结构生成」。树状目录只能选一个父节点，其余关系会丢失。固定目录还会产生「这一章还没写完」的债务感，抑制随手记录。

**呈现形式是维基百科版式。** 初版做成了极简的索引表，作者的反馈是「太素、太像博客」。改用维基版式后成立，理由有三：

1. **维基的红链本来就表示「这个条目还不存在」** —— 与本站「被引用但还没写」完全同义。不必另发明一套记号，而且所有人都认得。
2. **维基的密度不靠装饰**，靠的是信息框、目录、章节横线、参见、分类栏这些**本身携带信息**的框架。
3. **信息框正好装得下这类内容**：键长、pKa、Km、催化酶、典型浓度 —— 这些常查的定量事实在纯排版方案里没有地方安放。

## 3. 内容模型

### 3.1 条目

位置：`src/content/notes/**/*.{md,mdx}`

```yaml
---
title: 二硫键
tags: [蛋白质结构, 翻译后修饰]
aliases: [disulfide bond, S-S 键]   # 可选
infobox:                             # 可选
  - k: Sγ–Sγ 距离
    v: 2.05 Å
  - k: 催化
    v: PDI 家族 · Ero1
---
```

- **没有** `date` / `description` / `draft` —— 这些属于 blog
- `aliases` 让中文和英文都能链接过去
- `infobox` 可选，不填就不显示 —— 写作摩擦为零这条原则没有被破坏
- 正文用 `## 章节名`；**有两个以上章节时自动生成目录**，不需要手工维护

**文件名必须全小写、连字符分词**（`flow-matching.md`）。Astro 的 content collection 生成 id 时走 github-slugger（转小写、空格转连字符），文件名带大写或空格会与内部计算的 slug 不一致。构建期有断言会硬失败拦住这种情况。

**「最后更新时间」不由 frontmatter 提供**，构建时从 git 取（`git log -1 --format=%cI`）。取的是 `%cI` 原始字符串的前 10 字符 —— 那是**提交者本地的日历日**，与构建机时区无关（CI 跑在 UTC，用 `toISOString` 会差一天）。文件尚未提交时回退到 mtime，两者都取不到时回退当前时间并 `console.warn`。

### 3.2 氨基酸数据

位置：`src/data/amino-acids.yaml`

**这不是一套通用的「结构化数据系统」，而是全站唯一一份特例。**

判断某类内容该用数据驱动还是直接写 markdown 表格，标准只有一条：**是否需要从别的条目 `[[链接]]` 到单个条目**。需要 → 每条得有自己的页面 → 数据驱动；不需要 → 就是一张表，直接写在正文里。

字段：`code1` `code3` `name_zh` `name_en` `smiles` `mw` `pka_side?` `hydropathy` `charge` `polarity` `essential` `note`。schema 用 zod 严格校验，字段缺失构建失败（数据源唯一且可控，应当严格）。

氨基酸条目页的信息框、导言段落**都由这份数据自动生成** —— 表里和正文永远一致，不会出现「改了表忘了改文字」。

## 4. 双向链接机制

这是整个系统的核心，也是唯一需要自己实现的部分。

### 4.1 语法

```markdown
[[半胱氨酸]]
[[半胱氨酸|Cys 残基]]     显示为「Cys 残基」
```

### 4.2 解析优先级

`buildIndexWithCollisions()` 分三轮写入索引，每轮内先到先得：

1. 全部条目的 `title`
2. 全部条目的 `aliases`
3. 全部条目的 slug

匹配忽略大小写与首尾空白。

**同一轮内的胜负取决于 `loadTargets()` 的数组顺序**，当前是 `[...笔记, ...氨基酸]`，因此条目标题撞氨基酸中文名时**条目胜出** —— 你为半胱氨酸单独写了深入笔记，`[[半胱氨酸]]` 就该指向你写的那篇，而不是内置参考数据。这是有意决策，`targets.test.ts` 里有回归测试钉住顺序。

**氨基酸的单字母代号不作为别名。** `C`、`A`、`G` 太短，会与正文普通文本冲突（「维生素 C」「组 A 链球菌」）。别名只用 `name_en` 与 `code3`。

**键冲突不是错误，但必须知情。** 两个不同目标争同一个名称时，构建期打印警告，说明撞的是哪个名字、实际指向哪里、被压住的是谁、各自以什么身份（title/alias/slug）参与。**不硬失败** —— 为某个氨基酸单独写条目是合理需求，属于需要知情而非需要阻断。

### 4.3 未写的条目 = 红链

链接到还不存在的条目，渲染成**维基式红链**，指向占位页，页面内容是「本条目尚未撰写」加上「以下页面提到了它」。

这是刻意的：**红链就是待写清单**，从实际阅读需求中自然生长。首页的「缺失条目」框把它们汇总起来，那份清单是自动算出来的，不是手工维护的。

构建时在控制台输出所有未解析链接的汇总，但**不使构建失败**。

未解析名称转成路由 slug 时走 `placeholderSlug()`：在 `normalizeName()` 之上**只保留已知安全的字符**（Unicode 字母、数字、`-`、`_`），其余一律替换成 `-`。用白名单不用黑名单 —— 黑名单永远列不全（最初漏了换行符，跨软换行的 wikilink 会让构建崩溃）。退化结果的兜底值是 `unresolved~link`，`~` 会被 github-slugger 无条件剥离，所以真实条目 slug **结构上不可能**与它相同。

### 4.4 反链 =「参见」

构建时扫描全部条目建立链接图，每页底部渲染「参见」章节，进入目录编号。

维基的「参见」是人工列的，这里是自动算出来的 —— 谁提到了本条目，它就在那儿，不会漏。

**链接图以 `href` 为 key，不是 slug。** 条目与氨基酸的 slug 可能重名（`cys.md` 与氨基酸 `Cys`），href 按构造全站唯一。

**明确不做力导向关系图。** 节点超过五十个即为一团乱线，实际不用于导航。

## 5. 页面结构

| 路由 | 内容 | 进搜索索引 |
| --- | --- | --- |
| `/` | 本站概况框 + 缺失条目框 + 分类多栏条目表 + 氨基酸性质表引用 + 页脚最近编辑 | 否 |
| `/n/[slug]` | 条目：信息框 + 目录 + 正文 + 参见 + 分类栏 | 是 |
| `/n/[未写的名字]` | 红链占位页：谁提到了它 | 是 |
| `/tags/[tag]` | 「分类：X」，多栏条目列表 | 否 |
| `/aa` | 氨基酸速查表，可筛选排序 | 是 |
| `/aa/[code]` | 氨基酸条目：信息框（含现场渲染的结构式）+ 数据生成的导言 + 参见 | 是 |

**索引页与分类页整页排除出搜索索引。** 它们本来就是导航清单，连标题（「分类：蛋白质结构」）都会命中搜索词。用户搜一个词是想找**写了这内容的条目**，不是想找「哪个清单列出了它」。条目页的「参见」区块同理排除 —— 那是别的条目的标题，不该污染本条目的索引。

## 6. 视觉设计

取维基百科版式，忠实而非「借鉴」：

- **正文无衬线、标题衬线加下横线** —— 维基的分工。中文正文用无衬线更耐读
- 配色用维基的实际色值：链接 `#3366cc`、红链 `#d73333`、正文 `#202122`、边框 `#a2a9b1`、chrome 底 `#f8f9fa`
- 白底内容区 + 浅蓝细边框，灰底 chrome 条（含搜索框，常驻不占正文空间）
- **信息框与目录叠在同一右侧栏**，正文绕排。维基经典皮肤把目录插在导言之后，那需要把渲染好的正文切成两段；新版维基（Vector 2022）本就把目录移出正文当页面 chrome，这里沿用后者

字体：Noto Sans SC + IBM Plex Sans（正文）／ Source Serif 4 + Noto Serif SC（标题）／ IBM Plex Mono（代码、代号）。

## 7. 组件

| 组件 | 用途 |
| --- | --- |
| `Infobox.astro` | 浮右信息框，可带现场渲染的结构式 |
| `Toc.astro` | 目录框，章节来自条目自身的 h2/h3，带层级编号，少于两个章节不显示 |
| `Backlinks.astro` | 「参见」章节 |
| `Mol.astro` | `<Mol smiles="..." />` 小分子结构图 |
| `Structure.astro` | `<Structure pdb="1UBQ" />` 蛋白质三维结构 |
| `Search.astro` | Pagefind 搜索框（在 chrome 条里） |

### 7.1 小分子结构图

SmilesDrawer 2.4.1，客户端渲染 SVG。三条实测确认的事实：

- **渲染目标必须是 `<svg>`，不能是 `<canvas>`** —— `SmiDrawer` 底层走 `SvgDrawer`。用 canvas 会静默空白无报错
- ESM 是 default 导出：`import SmilesDrawer from 'smiles-drawer'`，取 `SmilesDrawer.SmiDrawer`
- 绘制签名：`draw(smiles, svgElement, theme, onSuccess, onError)`

SMILES 解析失败时原样显示字符串加提示，不影响页面其余部分。

### 7.2 蛋白质三维结构

Mol\* (molstar 5.11)，`molstar.Viewer.create()` 高层封装。**懒加载是硬性要求**：产物约 4.8 MB，页面初始只渲染占位卡片，点击后才注入 `<script>`。冒烟检查会断言页面里没有会立即触发下载的静态标签。

三个实测发现，都写进了实现：

- **`loadPdb` 在结构下载失败时不会 reject** —— promise 照常 resolve，错误只进 molstar 自己的日志。必须显式检查 `hierarchy.current.structures.length` 才知道是否真的加载成功
- 资源加载失败后必须重置 `assetsPromise`，否则「重试」按钮点了不发新请求
- 成功之前不要 `remove()` 按钮，否则失败时用户没有任何可点的东西

CSS 加载失败只降级（`console.warn`），不阻断 —— 样式不完整仍能看到结构。

## 8. 搜索

Pagefind，构建时生成静态索引。

**版本锁死在 `1.4.0`（精确版本号，不是 `^1.4.0`）。** 1.5.x 起查询端改用浏览器 `Intl.Segmenter`，与构建端的 Rust 分词器对中文复合词切分边界不一致，导致「二硫键」「谷胱甘肽」这类专业词**静默零结果**。README 有完整复现步骤，并点明只测「蛋白质」这种常见词是测不出来的。

## 9. 一条贯穿全局的原则：静默失败必须转为硬失败

这个项目在多处踩过「看起来正常、实际是错的」：Astro 静默覆盖同名页面、内容缓存产生陈旧渲染、搜索静默零结果、日期静默塌缩成构建时刻、占位页静默顶替真实条目。

因此构建期设了四道断言，**任一触发即中断构建并指出具体是哪个文件／名字**：

| 断言 | 防的是 |
| --- | --- |
| `assertUniqueSlugs` | 两个条目文件算出相同 slug（Astro 自身只 WARN 并静默覆盖） |
| `assertIdsMatchTargets` | `loadTargets()` 的 slug 集合与 collection 的 id 集合不一致 |
| `findPlaceholderNoteCollisions` | 占位页 slug 与真实条目 slug 撞车 |
| `sourcePath()` 的 filePath 检查 | Astro 内部结构变动导致日期取错 |

与之相对，**这些情况只警告不阻断**：未解析的链接（那是待写清单）、链接键冲突（那是合理需求）、molstar CSS 加载失败（降级仍可用）。

判据是：**会不会静默产出错误数据**。会 → 硬失败；只是需要知情 → 警告。

## 10. 构建与部署

```bash
npm run dev       # 本地预览（搜索不可用，见下）
npm run build     # 构建 + 生成 Pagefind 索引
npm run preview   # 预览构建产物（搜索可用）
npm test          # 单元测试（99 个）
npm run check     # 构建产物冒烟检查
```

**`dev` / `build` 都带 `--force`，不是可选项。** Astro 的内容缓存假设「一篇 markdown 的渲染只取决于它自己的内容」，但 wikilink 的解析取决于**全站条目集合** —— 新写一篇《米氏方程》后，其它条目里 `[[米氏方程]]` 的解析结果就变了。不带 `--force` 时缓存会端出旧渲染，那些链接会永远停在红链状态。

**Node 22+**（Astro 6.4 要求 `>= 22.12.0`，Node 20 下构建直接退出）。

部署：GitHub Actions → GitHub Pages，仓库 `Passion4ever/notes`，域名 `notes.passion4ever.org`。
CI 的 `fetch-depth: 0` 是必需的 —— 默认浅克隆会让 `git log` 取不到文件历史，所有日期塌缩成同一时刻。

**待办**：Cloudflare 加 CNAME 记录 `notes` → `passion4ever.github.io`，代理设为 DNS only（灰云），否则 GitHub 无法完成域名验证、签不出证书。

## 11. 测试

- `linkindex` / `wikilink` / `linkgraph` / `targets` / `gitdate` —— 99 个单元测试
- 重点覆盖：解析优先级、代码块内的 `[[x]]` 不被提取、`placeholderSlug` 的退化输入、跨模块一致性（`missingHref` 输出与占位页路由必须相等）、`loadTargets` 的数组顺序
- 构建冒烟检查 `npm run check`：结构性产物齐备、至少一篇条目页、含 `<Structure>` 的页面确实是懒加载
- 组件渲染依赖浏览器运行时，用 Playwright 人工验证过：结构图渲染、表格排序筛选、Mol\* 懒加载与错误路径、搜索命中
